# DogFinder

Сервис поиска пропавших собак: владелец публикует объявление о пропаже, нашедший — объявление о находке, система сама сопоставляет их по фотографии и географии и уведомляет владельца.

Ключевое отличие от обычной доски объявлений — поиск не по текстовому описанию («рыжий, средний, в ошейнике»), а по визуальному сходству фотографий. Текстовое описание собаки субъективно и плохо ищется; фотография объективна.

## Как это работает

1. Пользователь загружает фото и указывает место пропажи или находки.
2. Детектор находит на фото собаку и вырезает её, отбрасывая фон.
3. Нейросеть переводит изображение в вектор признаков (эмбеддинг).
4. При появлении нового объявления система ищет кандидатов: сначала фильтр по радиусу и дате, затем ранжирование по косинусной близости векторов.
5. Если найдено совпадение выше порога — владелец получает письмо.

Шаг 2 не косметический. Без вырезания собаки модель кодирует всю сцену целиком, и фотографии разных собак на похожем фоне оказываются «ближе» друг к другу, чем две фотографии одной собаки в разной обстановке.

### Почему pgvector, а не отдельная векторная БД

Поиск совпадений всегда комбинированный: визуальное сходство плюс расстояние плюс близость по времени. Если векторы держать в отдельном хранилище, а гео — в Postgres, придётся объединять два набора результатов в коде приложения. Это либо неполная выборка, либо медленный запрос. Один `SELECT` с фильтром по `ST_DWithin` и сортировкой по `<=>` решает задачу целиком.

### Почему модели не дообучаются

CLIP и YOLO берутся предобученными. Дообучение под конкретную задачу требует размеченного датасета пар «одна и та же собака в разных условиях», которого нет в открытом доступе в достаточном объёме. Готовых моделей достаточно, чтобы система работала.

## Требования

- Docker и Docker Compose
- [uv](https://docs.astral.sh/uv/) (менеджер пакетов Python)

Отдельно ставить Python не нужно — uv скачает нужную версию сам.

## Быстрый старт

```bash
git clone <url> dogfinder
cd dogfinder

cp .env.example .env
uv sync

docker compose up -d
uv run alembic upgrade head
uv run uvicorn app.main:app --reload
```

Значения в `.env.example` подходят для локального запуска как есть — менять их не требуется.

Доступные адреса:

| Адрес | Что это |
|---|---|
| http://localhost:8000 | приложение |
| http://localhost:8000/docs | документация API |
| http://localhost:8000/health | проверка состояния |
| http://localhost:9001 | консоль MinIO (`minioadmin` / `minioadmin`) |

## Проверка работоспособности

```bash
curl http://localhost:8000/health
```

Ожидаемый ответ:

```json
{"status": "ok", "postgis": "3.4.x", "pgvector": "0.7.x"}
```

## Разработка

```bash
docker compose stop     # остановить контейнеры
```

```bash
uv run alembic revision --autogenerate -m "описание"
uv run alembic upgrade head
uv run alembic downgrade -1
uv run alembic current
```


Линтер запускается автоматически перед коммитом через pre-commit:

## Известные ограничения

**Похожие породы.** Собаки распространённых пород визуально мало отличаются друг от друга. Для золотистого ретривера система вернёт десятки кандидатов с высоким сходством. Частично компенсируется фильтрами по радиусу, дате и метаданным, полностью не решается без индивидуальных признаков (клеймо, чип, особые приметы).

**Качество фотографий.** Модель чувствительна к ракурсу и освещению. Фотография со спины и фотография морды одной и той же собаки могут оказаться дальше друг от друга, чем фотографии двух разных собак в одинаковом ракурсе.

**Точность координат.** Координаты объявлений намеренно смещаются на случайную величину около 200 метров, чтобы объявление о пропаже не раскрывало домашний адрес. Точка на карте показывает район, а не конкретное место.

**Порог совпадения.** Значение подбирается эмпирически и балансирует между пропущенными совпадениями и ложными уведомлениями. Универсального значения не существует.

**Точность координат**. Координаты объявлений публикуются без изменений. Для объявлений о находке это необходимо: владелец ориентируется по точке, и погрешность в двести метров может стоить результата. Для объявлений о пропаже точка обычно расположена рядом с домом владельца, и вместе с именем и телефоном в том же объявлении это раскрывает больше, чем требуется. В production-версии разумным решением было бы смещение координат для объявлений о пропаже на случайную величину до 200 метров, детерминированное по идентификатору объявления, либо явный выбор пользователя при публикации. В текущей версии выбрана точность в пользу эффективности поиска.


### Производительность геопоиска

Замер на 100 000 объявлений со случайными координатами, PostgreSQL 16, радиус 5 км:

| Запрос | Индекс | План | Время |
|---|---|---|---|
| ST_DWithin | GIST | Index Scan | 6.8 мс |
| ST_DWithin | нет | Parallel Seq Scan | 99.5 мс |
| ST_Distance < 5000 | GIST | Parallel Seq Scan | 100.6 мс |

Третья строка показывает, что наличие индекса само по себе ничего не гарантирует.
ST_Distance вычисляется для каждой строки таблицы, и планировщик не может
использовать пространственный индекс. ST_DWithin сначала отбирает кандидатов
по ограничивающим прямоугольникам через индекс и применяет точную геодезическую
формулу только к ним — в плане это видно по строке Rows Removed by Filter,
где из 14 отобранных индексом кандидатов отсеиваются 6.
